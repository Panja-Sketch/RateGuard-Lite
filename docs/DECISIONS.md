# Decisions log

Where the build specification (v1.1) was ambiguous or in tension with itself, the option that **fails closed** was chosen and recorded here.

| ID | Decision | Why |
|---|---|---|
| D-001 | Config lives in the repo-level `config/` folder, found via `RGL_CONFIG_DIR`, else by walking up from the package. Install with `pip install -e .` (the setup scripts do). | Spec 14/15 puts `config/` at the repo root. A non-editable wheel install would not find it. |
| D-002 | The canonical model (`CellValue`, `Row`, `RateTable`, ...) uses **frozen slotted dataclasses**, not pydantic. Pydantic remains for config, Jira scope, findings and the report. | These objects are built only by our own code; pydantic validation was ~25 µs/cell and dominated a 600k-cell run. |
| D-003 | Guidewire exports are read by a small **lxml** values-only reader (`ingest/fastxlsx.py`); openpyxl is used for approved workbooks (needs formatting). Entities, DTDs and network access are disabled. | openpyxl falls back to pure-Python `defusedxml` parsing (~46 µs/cell). Needed for the A6 targets. |
| D-004 | A table pair is **CONFIRMED** without a learned alias when identity is exact: same table number *and* name similarity >= 0.85, or identical normalized names with matching key columns and no conflicting number. Similarity-only matches (>= 0.80, margin >= 0.10) are **SUGGESTED** and cap the verdict at `NEEDS_REVIEW`. | Otherwise the very first run could never be `PASS`, contradicting A1/A3. Ties are never exact. |
| D-005 | Conflicting Jira actions for one table are **always** `NEEDS_REVIEW` (the comment-timestamp "latest wins" rule is not implemented). `JiraScope` has an extra field `review_flags`. | Fails closed. Pasted Jira exports rarely carry comment timestamps. |
| D-006 | `MISSING_UPDATE` is raised only when the export is unchanged vs the baseline **and** the approved table does not equal the export. If approved = export = baseline for a declared update, it is an INFO `APPROVED_ROW_UNCHANGED`. | Approved tables are FULL (spec 2, 6.4), so "export equals approved" means the intended state is in place. |
| D-007 | An approved table with no confident match is `NEEDS_MAPPING` (BLOCKED) when its best candidate scores >= 0.20; below that it is `TABLE_MISSING_IN_EXPORT` (CRITICAL). | Cannot tell "not loaded" from "named differently" without a plausible candidate. |
| D-008 | In a Guidewire export, an **interior fully blank row is data** (wildcard keys, blank factor). | This is exactly the "blanks loaded instead of wildcards" production defect. Approved workbooks may have gaps, which are skipped. |
| D-009 | The weak `_123_` table-number pattern is used for scoring only, never for table identity. | A filler code such as `BOP_Roof_001_Ext` would otherwise collide with real table 1. |
| D-010 | `python-dateutil` is not used; dates are parsed by a strict own parser. | dateutil guesses; the spec says ambiguous dates must be `NEEDS_REVIEW`. |
| D-011 | Effective date: book-level (majority of table metadata) must equal the Jira filing date; table-level only for approved/declared tables. | A new rate book edition shares one effective date; unchanged tables are not expected to differ. |
| D-012 | Engine D (ranges) and export-side integrity checks run on approved tables, their export counterparts, and export tables changed vs baseline. Unrelated legacy tables are not audited. | Pre-existing defects in untouched tables should not fail an unrelated change. |
| D-013 | `OPEN_END_MISSING` is raised only when the last band's max is a true BLANK that is not enabled as a wildcard. | Blank max is open-ended by default (wildcard); the rule covers the case where it is not. |
| D-014 | Tables with Jira action BYPASS are excluded from Engine A; they are checked by Engine B (`BYPASS_VIOLATION`). | A bypassed table's approved rows are not the target state. |
| D-015 | Every run stores an `UNVERIFIED` snapshot. `rgl snapshot take` records a `VERIFIED` one (explicit user action). A snapshot from a FAIL/BLOCKED run cannot be accepted. | Spec 8.7: only user-confirmed passing exports become baselines. |
| D-016 | Identical duplicate keys in an **export** are a WARNING; any duplicate in an approved table, or duplicates with different values, are a BLOCKER. | Literal reading of spec 5.7. |
| D-017 | Input-file warnings (external links, OLE) become `INPUT_WARNING` findings, so they cap the verdict at `PASS_WITH_WARNINGS`. Macro presence is INFO only. | Spec 5.1. |
| D-018 | `MATCH_ROUNDED` findings are capped at 500 per table (the count is still exact in the summary). | Keeps reports usable when a whole table is rounded. |
| D-019 | Pair IDs follow the approved table's identity (`{LOB}:{number}` or slug); export identity is used for export-only tables. | Stable across runs for the same workbook. |
| D-020 | Learned **layout fingerprints** are stored but not yet applied to header detection; `rgl map` resolves table mappings and hidden sheets. New layouts are calibrated via `config/gw_layouts.yaml`. | Time-boxed; the detection never guesses, so the gap is safe (NEEDS_MAPPING). |
| D-021 | The optional local-LLM Jira assist is not implemented (config flag exists, default off, loopback-only by validation intent). | Out of scope for the core; default is off. |
| D-022 | The fixture generator lives in `src/rateguard_lite/samples/generator.py`; `tests/fixtures/generator.py` re-exports it. | `rgl sample` and `rgl selftest` ship with the package. |
| D-023 | Large fixture tables: "large" (10k-30k rows) tables are `max(1, tables // 60)` per workbook, so a 120-table export has ~160k cells, a 220-table export ~330k. | Keeps fixture generation fast; the performance targets are met with margin (220 tables ~10 s, ~470 MB). |
| D-024 | **Product decision: the same rate book rarely changes twice, so Snapshot History adds little.** (1) `snapshots.enabled` defaults to `false`; the end-of-run "accept snapshot?" prompt is gone (CLI and UI). `rgl snapshot ...`, `--accept-snapshot` (which switches snapshots on for that run) and `--profile snapshots` remain for anyone who opts in. (2) New `verdict.require_baseline_for_pass` (default `false`): with no baseline and no other issue the verdict is `PASS` (exit 0) and every report carries "Scope check (tables outside approved/Jira): not performed – no baseline provided". `true` (profile `strict_baseline`) keeps `PASS_WITH_LIMITATIONS` + `NOT_EVALUATED_NO_BASELINE`. (3) New check `OUT_OF_SCOPE_TABLE_DATED` (NEEDS_REVIEW): an export table that is not in the approved file and not in Jira, whose own effective date equals the Jira filing date or whose edition equals the export's new edition. Skipped silently, with a note in `run_manifest.json` (`check_notes`), when the export has no per-table dates/editions, or when every table carries the identical stamp (a book-level stamp cannot single out a table; without this guard a normally stamped new edition would flag every unchanged table). (4) `config/team_mappings.yaml` is the primary source of CONFIRMED aliases, column roles, wildcards, etc. `rgl review` / `rgl map` / `rgl learn confirm` write there with `confirmed_by` and `confirmed_on`; the local SQLite store keeps only PROPOSED items (skipped review items, imported files) and run history. Legacy `CONFIRMED` rows in an older `learning.db` are still read (team file wins) and can be moved with `rgl learn export`. Team items have ids like `T-1a2b3c`; `rgl learn retire T-...` removes one. `RGL_TEAM_MAPPINGS` overrides the file location (tests, self-test). | The snapshot prompt added friction for little value. Confirmed mappings are team knowledge, so they belong in a reviewed, versioned file rather than a per-machine database. Mapping still never changes comparison math or verdicts. |
| D-025 | **Typing and redirected output.** (1) `mypy --strict` is now clean on the whole package (type-only fixes in `samples/generator.py`, `cli.py inspect`/`stats`, `ui/app.py`; no behaviour change). (2) The CLI reconfigures stdout/stderr to UTF-8 with `errors="replace"` at start, and shows the rich spinner only when stdout is a TTY, so `rgl run > $null` or `> file` no longer raises `UnicodeEncodeError` (Windows treats NUL as a console, so the encoding fix is the real guard). A subprocess test redirects stdout to a file under a cp1252 code page. | Output redirection is routine in scheduled or scripted use; unencodable characters degrade to `?` instead of an internal error (exit 4). |
| D-026 | **Test prioritization: a short, risk-ranked "Must Test" list.** RateGuard-Lite already compares every cell, so QA quotes no longer re-check factor values row by row. The default `test_scenarios.xlsx` has a **Must Test** sheet (default 12 tests, `tests.max_must_tests`, hard cap 20, always at least 3) and an **All Candidates** sheet with every scored candidate and how its score was built. Categories C1-C11 cover what a file comparison cannot prove: rate book selection on the filing date (C1), renewal (C2), mid-term change keeps original rates (C3), non-premium change (C4), changed table is used in rating (C5), range edges (C6), wildcard rows (C7), new keys (C8), out-of-scope control (C9), fix retests (C10, always included and ranked first), flat cancellation (C11, only when the story mentions fees, surcharges or cancellations). Score = 40 fix retest + 25 date/rate book + 20 new key or table + 15 range edge + 10 x min(1, change/10%) + 10 wildcard + 5 story names it; ties go to tables named in Jira, then the stable test ID. Max 2 tests per table (not C10). One quote that proves two things is combined (the filing-date quote takes the highest-scoring changed table, noted in the test). `verdict.txt`, the HTML report and the Jira comment show only the Must Test list plus the line "Full candidate list: test_scenarios.xlsx > All Candidates". `--tests full` also writes the earlier Parameter Tests / Transaction Matrix sheets. JSON changes are additive (`test_scenarios.must_tests`, `must_test_count`, `all_candidates_count`). **Judgement call:** C4, C9 and C11 carry no table-specific risk, so they use a fixed base score of 12 (plus 5 when the story names them); without this they would never rank. | Testers have limited time. The cell-by-cell comparison is the proof for values; human quotes are for date logic, rating use and edges. Nothing is removed, only ranked. |
| D-027 | **Plain-language messages for QA analysts and actuaries.** Every finding has three plain parts: what we found, why it matters, what to do (`plain_what`, `plain_why`, `plain_action`, rendered from templates in `config/messages.yaml` and named by table, row in business terms, file, tab and cell). The old `explanation` and `suggested_fix` fields stay and now hold the plain text. Rule ID, raw values and cell references move to a "Technical details" column (Excel), a folded section (HTML) and the existing JSON fields (`rule_id`, `message`, `details`, `approved_value`...). Verdict headlines and the no-baseline scope line use the agreed wording; severity codes are shown with plain labels (for example "Not checked" instead of NOT_EVALUATED) but the codes stay in JSON. Input errors (missing file, wrong type, password-protected, open in Excel, damaged, empty tab, headers not found) say what happened and what to do. The HTML report and the UI start with a "How to read this report" box. Tests fail if any main-text message contains banned jargon or a raw rule ID, or if a finding lacks a part. Finding IDs, verdict logic, exit codes and CLI flags are unchanged. | Reports were written for developers. QA and actuaries need to act on them without knowing internal terms. |
| D-028 | **Must Test list no longer pads to the cap; range bands read in business words.** (1) `tests.max_must_tests` defaults to 8 (hard cap 20 unchanged). Any candidate scoring below 20 is left out of Must Test (fix retests are exempt), so a one-table change typically gives 3-6 tests. C4, C9 and C11 appear in Must Test only when the Jira story mentions the topic (endorsements/policy changes; other states or lines; cancellations/fees); otherwise they stay in All Candidates with the note "The story does not mention ...". Their base score is now 15, plus 5 when the story mentions them, so a mentioned control test scores exactly 20 and qualifies. (2) Range keys are shown as "4 to 6 stories", "10 or more stories" or "4 stories" in findings, reports and the UI, using the field_map label for the unit when one matches. Quote set-up text names the band column without the From/To suffix ("Stories = 4"). The raw headers stay in Technical details and JSON. | A short list that is padded with generic tests is not a priority list. "Stories From = 4, Stories To = 6" reads like a database row, not a business statement. |
